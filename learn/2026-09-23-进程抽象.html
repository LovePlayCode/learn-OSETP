2核心概念闭卷自测（点击展开前，先在心里/纸上说一遍）

Q1. 进程和程序的区别？A层
程序是躺在磁盘上的静态代码/数据；进程是程序被加载运行后的"活的状态"。一份程序（菜谱）可以同时对应多个进程（多个人同时按它做菜）。
今天踩过的坑：一开始说反了方向——"进程是程序的一部分"。正确方向是"进程 ⊇ 程序在运行时的状态"，不是程序包含进程。
Q2. 这一章的"关键问题"原句是什么？它和"隔离/互不影响"是同一件事吗？A层
原句："虽然只有少量的物理 CPU 可用，但是操作系统如何提供几乎有无数个 CPU 可用的假象？"——这问的是数量幻觉（能不能让少数CPU看起来像很多个），不是隔离保护（互不影响，是虚拟内存章节的主场）。
今天踩过的坑：两次把"数量/并发"家族和"隔离/保护"家族搞混，是本次学习最大的元层级问题。
Q3. 进程的机器状态由哪三部分组成？A层
① 内存（地址空间） ② 寄存器（其中 PC / 栈指针 / 帧指针是寄存器的特殊子集，不是并列的第三类） ③ I/O 信息（打开的文件列表）。
今天踩过的坑：把"寄存器"和它的子集"PC/SP/FP"并列成了平级的兄弟，还漏掉了 I/O 信息这一整块。
Q4. 机制 vs 策略，为什么要故意分开设计？A层
这是模块化（modularity）的软件设计原则：机制负责"怎么做"（如上下文切换），永远不变；策略负责"选哪个"（如调度算法），可以随时替换，不用重新考虑机制。
验证过的两个类比：①缓存淘汰——"怎么删数据"是机制，"选哪条删"（LRU/LFU）是策略。②反例：实时系统有时故意不分离，为了避免间接调用带来的不确定性，牺牲灵活性换取确定性（determinism）。
Q5. 默画进程三态转换图（这是今天默画通过的版本）A层
就绪 --调度(scheduled)--> 运行　|　运行 --取消调度(descheduled)--> 就绪　|　运行 --I/O:发起--> 阻塞　|　阻塞 --I/O:完成--> 就绪
今天踩过的坑：一开始漏掉"运行→就绪"这条线（不知道纯 CPU 进程之间怎么轮换）；也把"阻塞→就绪"错写成"阻塞→运行"，忘了 I/O 完成后还要重新排队等调度。

3实践验证：两种调度策略对比（纸笔推演）

Process A：CPU、CPU、发起I/O(耗时2单位)、CPU，结束　|　Process B：CPU、CPU、CPU、CPU，结束

情况① SWITCH_ON_IO + IO_RUN_IMMEDIATE（一阻塞就换人，I/O好了立刻抢回来）

时间AB注
1运行就绪A 第1步
2运行就绪A 第2步，结束时发起 I/O
3阻塞运行立刻切到 B
4阻塞运行结束时 I/O 完成
5运行就绪立刻抢回来，A 跑完最后一步并结束
6—运行B 第3步
7—运行B 第4步，结束

总耗时 7 · CPU 利用率 7/7 = 100%（A 等设备的两格，CPU 拿去跑了 B）

情况② SWITCH_ON_END（死等 A 彻底结束才考虑切换）

时间AB注
1运行就绪A 第1步
2运行就绪A 第2步，结束时发起 I/O
3阻塞就绪CPU 空闲——不切到 B
4阻塞就绪CPU 空闲，结束时 I/O 完成
5运行就绪A 跑完最后一步并结束
6—运行B 第1步
7—运行B 第2步
8—运行B 第3步
9—运行B 第4步，结束

总耗时 9 · CPU 利用率 7/9（第3、4格 CPU 白白空转）

结论（综合追问的回答）

情况①吞吐更高、CPU 不浪费，通常更优；但当"绝对不被打断"本身就是价值时——例如需要保证操作不可分割完成、避免不可预测的抢占时机（真实场景：某些实时系统追求确定性）——情况②的"死等到底"反而是合理选择。这印证了资料里那句悬念："这是不是一个好决定？由调度策略决定，答案不唯一。"

4盲点自查清单（今天真实踩过的坑，下次复习前先自己检查一遍）

  • 程序 vs 进程，方向别搞反——是"进程装着运行时状态"，不是"进程是程序的一部分" 检查方法：能不能说出"一份程序可以同时对应几个进程"
  • "关键问题"问的是数量幻觉，不是隔离/互不影响——这是本次最大的元层级混淆点 检查方法：被问"进程解决了什么问题"时，第一反应是不是又飘向了"安全/隔离"
  • 机器状态三大块里，别把"寄存器"和它的子集"PC/SP/FP"并列成兄弟 检查方法：能不能一次性说全三大块，且不重复不错位
  • 阻塞态结束后，先回到"就绪"，不是直接"运行"——中间还要再被调度一次 检查方法：默画三态图时，"阻塞→?"这条箭头终点是哪个框
