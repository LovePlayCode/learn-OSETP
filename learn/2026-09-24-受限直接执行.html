第 6 章　机制：受限直接执行

学习目标：能完整默写「时钟中断 → 上下文切换 → return-from-trap」的时序，并说清"机制/策略"的分界线在哪

关键问题：如何高效、可控地虚拟化 CPU？

完整三层家族图

受限直接执行 LDE（总纲）
│  目标：如何【高效】且【可控】地虚拟化 CPU   ← 两个词，缺一不可
│
├── 子问题一：受限制的操作
│   │
│   ├── 答案层：CPU 提供两种模式  ←「一个人戴两顶帽子」
│   │   ├── 用户态 user mode      （同一块 CPU / 同一批寄存器，只差一个模式位）
│   │   └── 内核态 kernel mode
│   │
│   └── 通道层：程序怎么安全地跨过这条界
│       └── 系统调用（open/read…，为什么"看起来像过程调用"）
│           └── 靠【陷阱 trap】指令实现          ← 这是"跳"这个动作
│               └── 跳到哪，由【陷阱表 trap table】决定 ← 这是"地址簿"
│                                            （启动时由内核设置，特权操作）
│
└── 子问题二：进程之间切换
    │
    ├── 前置难题：重获控制权（regain control）
    │   ├── 协作方式 ── 等系统调用 / yield（把控制权"要"回来）
    │   └── 非协作方式 ── 时钟中断（把控制权"抢"回来）★ 本章主角
    │        └── 🔑 与左边对称：时钟中断处理程序的地址，
    │              同样是启动时由内核登记进【陷阱表】的
    │
    └── 实现动作：上下文切换 context switch
        └── 保存 A 的寄存器 → 切换内核栈 → 恢复 B 的寄存器
            └── 背后是调度程序 scheduler 的"决定"  ← ⚠️ 这是策略，全章唯一一处
三句话记牢这一章：
可控 = 边界（两顶帽子） + 通道（系统调用） + 强制力（时钟中断）
高效 = 直接执行（不翻译、不搬家） + 模式切换成本≈0（只翻一个模式位）
"受限"之所以加得上去，恰恰是因为"直接"没有被破坏。

2核心概念闭卷自测（点击展开前，先自己说一遍）

Q1. 本章的两个"关键问题"分别是什么？A层
问题1（6.2）：进程需要执行 I/O 和其他受限制的操作，但怎么才能不让它完全控制系统？
问题2（6.3）：操作系统如何重获 CPU 的控制权（regain control），以便在进程之间切换？
今天踩过的坑：问题1 一开始答成泛泛的"操作系统安全"——那是"感受"，不是"问题"。准确的说法是「受限制的操作」。问题2 完全想不起来，但它占了 6.3〜6.5 整整三节。
Q2. 用户态 / 内核态，是"两个房间"还是"一个人戴两顶帽子"？A层
是同一个人戴两顶帽子。CPU 是同一块，寄存器是同一批，代码没有搬家——变的只是 CPU 内部的一个模式位（mode bit）。

为什么这个区别至关重要（今天第一次答漏的半句）：
① 切换模式不搬家、不重新加载，代价几乎为零 → "直接执行"该有的「快」保住了；
② 这个模式位只能由 trap / 中断 / return-from-trap 等硬件事件改写，用户代码没有任何办法自己翻 → "受限"该有的「稳」也成立了。

一句话：如果是"两个房间"，进程就能自己走过去，控制权就丢了。
今天踩过的坑：答对了"两顶帽子"，但漏掉了"为什么重要"这半句——这是同一形状错误的第 3 次出现。
Q3. 为什么不能让进程自己设置陷阱表？A层
因为"设置陷阱表"本身就是一个特权操作——它就是被限制的东西之一。

推演链：陷阱表规定"发生事件 X → CPU 跳到地址 Y"。若进程能改写它 → 把表项指向自己的代码 → 触发一次 trap → CPU 切进内核态，却跳进了进程自己的代码 → 一段用户代码戴着内核态的帽子在跑。

后果：可读写任意内存、关掉时钟中断、把陷阱表改成"永不切换"、永远霸占机器。

🔑 要焊死的一句：陷阱表之所以安全，不是因为内容写得好，而是因为"改它的资格"本身被硬件锁死了。
Q4. 甲（执行除零指令）和乙（合法但永不调系统调用的死循环），OS 分别靠什么夺回 CPU？A层
不是同一条路径。
甲：除零指令乙：健康但死循环
谁触发进程自己（异常）没有任何人
靠什么机制陷阱 trap时钟中断 timer interrupt ★
属于哪一类协作方式非协作方式
OS 能做什么拿到控制权，可能直接终止违规进程拿到控制权，可切换到别的进程
删掉时钟中断后仍能抓到系统彻底失控，只能 reboot
最容易答错的陷阱：甲看起来是"意外"，为什么归到「协作方式」？
🔑 因为「协作 / 非协作」的划分标准不是"进程乐不乐意"，而是"OS 拿到控制权是否需要依赖进程先做点什么"：
· 甲：进程触发了异常（哪怕不情愿），OS 才拿到控制权 → 依赖进程行为 → 协作
· 乙：进程什么都没做，也永远不会做 → OS 完全无从下手 → 必须外部强制 → 非协作
所以乙才是这一章真正的主角。没有时钟中断，昨天学的三态图里"运行→就绪"那条箭头根本不会发生。
Q5. 默写「时钟中断 → 上下文切换 → B 继续运行」的完整时序（本次 11 步全对）A层
#发生了什么谁做的
1A 在用户态运行程序 A
2时钟中断发生硬件
3把 A 的用户态寄存器保存到 A 的内核栈硬件自动（隐式）
4转向内核模式，跳到陷阱处理程序硬件（地址来自陷阱表）
5内核决定切换到 B调度程序 scheduler ← 这是策略
6把当前内核寄存器保存到 A 的进程结构OS 显式（软件）
7从 B 的进程结构恢复 B 的内核寄存器OS 显式
8现在看起来就像 B 刚刚陷入内核——
9执行 return-from-trap硬件
10从 B 的内核栈恢复 B 的用户态寄存器硬件
11B 继续运行程序 B
💎 本页最重要的一处洞察（自己答出来的）：
寄存器保存发生了两次，主体不同——
· 第 3 步：硬件「自动」保存用户寄存器（隐式）
· 第 6 步：OS「显式」保存内核寄存器（软件）
很多人读完只会说"寄存器被保存了"，感觉不到这层主体差别。能感到它，说明是真读进去了。
小提醒：第 5 步的"决定"属于策略，第 6/7 步的"保存/恢复"属于机制。这一章全篇讲机制，唯一一处提到策略，就在这里。
Q6. 为什么把"机制"和"策略"分到两章去讲？（本次由学习者独立提出质疑后深挖）A层
书籍层面的答案（这才是问题本身）：
① 依赖顺序：你没办法评价一个调度策略，除非先知道机制能提供什么。第 7 章所有算法都建立在"时钟中断一响随时能切"这个前提上——那是第 6 章给的。
② 全书节拍器：这不是特例。后面内存虚拟化里，「分页（paging）= 机制」，「页面置换算法（LRU/Clock）= 策略」，同一个动作再来一遍。书在用同一套节拍反复训练同一个思维动作。
③ 分清「事实」与「选择」：机制是已经定下来的地面（该记住），策略是仍有争议的设计空间（该有自己的观点）。混在一起讲，学生会把策略当定理背，或以为机制也能随便挑。

工程层面的答案（补充视角）：机制几十年几乎不变，策略有几十种且不断出新。用一个稳定的、被反复验证过的机制，去承载一个不断变化的策略——换策略时，机制一行都不用改。

🔬 最硬的证据（自己读过的那行代码）：
void switch(struct context *old, struct context *new);
它只知道"存这个、恢复那个"，完全不知道"为什么是这两个"——"为什么"在调用它之前就被决定好了，是从外面传进来的两个指针。机制和策略之间，只靠两个指针通信。

🔮 目录本身就是宣言：这一章叫「机制：受限直接执行」，接下来连着三章叫「调度」。

本次踩坑：第一次答成循环论证——"因为是操作系统教程，需要分开讲"，等于没说。这是典型的"退步到抽象命题"现象。
Q7. 纵向三问：为什么这样设计 / 不这样设计会怎样 / 有没有替代方案？A层
纵向一 · 为什么需要两顶帽子？
杀招是递归：你想拦一个坏操作——好，谁来执行"拦"这个动作？还是代码。代码跑在哪儿？还是跑在那块只有一种模式的 CPU 上。那么拦人的代码，和要被拦的代码，权限一模一样——于是"拦截"在物理上不成立了。
🔑 所以两顶帽子的本质，不是"给操作系统多点权力"，而是——让"更高"这个东西，第一次在物理上存在。只有一顶帽子，保护不是"被绕过"，而是压根不存在。

纵向二 · 只有一种模式，攻击者能做什么？
① 改写陷阱表 → 让 trap 跳进自己的代码，穿着内核态跑；
② 关掉时钟中断 ★ ← 最致命。时钟中断是"非协作方式"的唯一武器，关掉它，OS 永远拿不回控制权，进程独占整台机器；
③ 随意读写别的进程的内存、进程结构体。

纵向三 · 软件逐条检查行不行？（本章灵魂）
画面：门卫扫一眼证件（便宜）× 门卫把每件行李逐件登记检查（贵十倍）——而人流是每秒几十亿条指令。
若让 OS 逐条检查，程序就不再是"直接跑"在 CPU 上，而是变成了被软件逐条解释执行（相当于一个解释器），速度会慢几个数量级。
🔑 所以这一章只能叫"直接"执行——因为"直接"两个字本身就是性能的全部来源。而"受限"之所以能加得上去，恰恰是因为"直接"没有被破坏。

3连接构建：第4章 ←→ 第6章

昨天（09-23）学的「进程三态图」是抽象；今天学的机制是它的物理实体。

第 4 章的抽象（昨天）第 6 章的物理实现（今天）
运行 → 就绪（取消调度 descheduled）时钟中断 + 上下文切换（11 步时序）
就绪 → 运行（调度 scheduled）调度程序 scheduler 的决定 + return-from-trap 跳进 B
运行 → 阻塞（发起 I/O）系统调用 → 陷阱 trap → 进入内核
进程的"机器状态"上下文切换保存/恢复的那堆寄存器 + 内核栈
🎯 一句话焊接：昨天那个抽象的"取消调度"箭头，今天有了物理实体——时钟中断动手、硬件隐式存用户寄存器、OS 显式存内核寄存器、切换到 B 的内核栈、return-from-trap 恢复 B。
没有时钟中断，三态图里"运行→就绪"那条箭头根本不会发生。
