第9章：比例份额调度

学习日期：2026-09-29

📌 核心理念

调度目标的根本转变

比例份额调度的核心目标：确保每个进程获得一定比例的 CPU 时间

与之前学习的调度算法（SJF、MLFQ）完全不同：

  • MLFQ：优化响应时间和周转时间
  • 比例份额：保证资源分配的公平比例

🎫 彩票调度 (Lottery Scheduling)

基本原理

彩票数代表份额：拥有 X% 的彩票 → 期望获得 X% 的 CPU 时间

进程份额 = 进程彩票数 / 总彩票数

工作机制

  1. 每隔一个时间片，进行一次彩票抽奖
  2. 生成一个随机数（中奖号码）：0 到 (总彩票数-1)
  3. 遍历进程链表，累加彩票数，直到超过中奖号码
  4. 当前进程就是中奖者，运行它
// 核心算法 int counter = 0; int winner = getrandom(0, totaltickets); node_t *current = head; while (current) { counter = counter + current->tickets; if (counter > winner) break; // 找到中奖者 current = current->next; } // current 就是中奖进程

三个扩展机制

  • 彩票货币 (Ticket Currency)：用户可以用自己的货币给子任务分配彩票，操作系统自动兑换成全局货币
  • 彩票转让 (Ticket Transfer)：客户端可以临时将彩票转给服务端，加速服务端执行
  • 彩票通胀 (Ticket Inflation)：进程可以临时提升/降低自己的彩票数（仅适用于互相信任的环境）

特点

  • 利用随机性，实现简单
  • 无需维护全局状态（每个进程只存自己的彩票数）
  • 新进程加入容易（只需更新总票数）
  • 概率上满足比例，但不是确定的（短时间可能不公平）

🎯 步长调度 (Stride Scheduling)

核心思想：确定性地实现比例分配

步长调度解决了彩票调度的概率性问题，能够精确控制比例

关键概念

步长 (stride) = 大数 / 票数
行程值 (pass) = 累计步长

票数多 → 步长小 → 行程值增长慢 → 长期处于最小 → 被调度频率高 → CPU 时间多

调度规则

// 伪代码 current = remove_min(queue); // 选行程值最小的进程 schedule(current); // 运行一个时间片 current->pass += current->stride; // 行程值增加一个步长 insert(queue, current); // 放回队列

核心：每次选择行程值最小的进程运行

例子：A(100票)、B(50票)、C(250票)

  • 步长：A=100, B=200, C=40（用10000除以票数）
  • 初始行程值都是0
  • 调度顺序：A→B→C→C→C→A→C→C→...
  • 结果：C 运行5次、A 运行2次、B 运行1次，正好是 250:100:50

特点

  • 确定性地实现比例（每个调度周期后都精确）
  • 需要维护全局状态（每个进程的行程值）
  • 新进程加入困难（行程值设为0会导致独占CPU）

⚖️ 彩票调度 vs 步长调度

维度 彩票调度 步长调度
实现方式 随机抽奖 选最小行程值
比例精确性 概率上满足（长时间才准确） 确定性满足（每轮都准确）
全局状态 不需要（只需总票数） 需要（每个进程的行程值）
新进程加入 容易（更新总票数即可） 困难（行程值设为0会独占）
实现复杂度 简单 相对复杂
短时间公平性 较差 优秀

🔗 与 MLFQ 的连接

调度目标的根本差异

MLFQ（第8章）：

  • 目标：优化响应时间（交互式任务）和周转时间（批处理任务）
  • 适用场景：通用操作系统（Linux、Windows）
  • 无需事先知道进程特性，自动调整优先级

比例份额调度（本章）：

  • 目标：按比例公平分配 CPU 时间
  • 适用场景：虚拟化数据中心（如 VMware ESX）、需要明确资源分配比例的环境
  • 需要事先确定每个进程应该拿多少份额

为什么通用OS用MLFQ而不用比例份额？

  1. 票数分配问题没有确定的解决方式（如何决定浏览器应该拿多少票？）
  2. 不适合 I/O 密集型进程（大部分时间在等待，不在CPU上）

🎯 盲点自查

关门复述检查点

  • 能否用自己的话解释：彩票调度如何通过随机数找到中奖进程？
  • 步长调度中，为什么步长要用"大数/票数"这个反比关系？
  • 为什么步长调度每次选"行程值最小"的进程？
  • 新进程加入步长调度系统，如果行程值设为0会发生什么？为什么？
  • 彩票调度为什么不需要全局状态，而步长调度需要？
  • 比例份额调度为什么没有被广泛用在通用操作系统的CPU调度上？

易错点

  • 彩票调度不是"直接计算"：不是直接算出中奖号码在哪个进程，而是遍历链表、累加彩票数、直到超过中奖号码
  • 步长调度的因果链：票数多 → 步长小 → 行程值增长慢 → 更容易成为最小 → 被调度更频繁
  • 不公平性指标U：工作运行时间短时，彩票调度的不公平性很高；只有长时间运行，才能趋于期望比例

💡 关键公式与代码

彩票调度核心

进程份额 = 进程彩票数 / 总彩票数

中奖号码范围：[0, 总彩票数-1]

步长调度核心

步长 = 大数 / 票数
行程值 += 步长（每次运行后）

调度规则：选择行程值最小的进程

不公平性指标

U = 先完成的时间 / 后完成的时间

U 越接近1，越公平
