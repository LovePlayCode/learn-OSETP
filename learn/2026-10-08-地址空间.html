第13章：抽象：地址空间

学习日期：2026-10-08

📌 核心问题

只有一块物理内存，怎么让很多进程都觉得"内存是我一个人的"？

操作系统给每个进程提供一个巨大的、稀疏的、私有的地址空间。进程只看到自己的虚拟地址，操作系统在专门硬件的帮助下，把每一个虚拟地址翻译成物理地址。

这是内存虚拟化的起点，后面的地址转换、分段、分页都是在回答"这个翻译具体怎么做"。

🕰️ 历史演进（B层）

每往前走一步，都是被新需求逼出来的

早期系统：内存里只有 OS + 一个程序 │ 需求：机器太贵，不能闲着 ▼ 多道程序：多个进程准备好，轮流用 CPU（追求利用率） │ 需求：人想马上看到程序的反应（交互性） ▼ 时分共享 v1：切换进程时把整块内存存到磁盘，换回来再读回 │ 问题：磁盘比内存慢太多 ▼ 时分共享 v2：多个进程同时留在内存里 │ 新问题：A 进程可能读写 B 进程的数据 → 需要保护 ▼ 地址空间抽象（让每个进程都以为自己独占内存）

学习中漏掉的一环是时分共享。"把内存存到磁盘"正是它最早的实现办法。

🧱 地址空间（A层）

地址空间是整体，虚拟地址是里面的"坐标"

【地址空间】← 最上层：OS 给进程的抽象，进程眼中自己独占的整块内存 │ ├── 代码 ├── 堆 ├── 栈 ← 组成部分（布局） │ └── 里面每一个位置的编号 = 虚拟地址 │ （OS + 硬件 翻译） ▼ 物理地址（内存条上真实的位置）

典型布局（以 16KB 地址空间为例）

0KB ┌──────────────┐ │ 代码 │ 大小固定，运行时不变 → 放在一端 1KB ├──────────────┤ │ 堆 ↓ │ malloc 分配的数据，往大地址增长 │ │ │ （空闲） │ ← 堆和栈共享这片空间，谁需要就给谁用 │ │ │ 栈 ↑ │ 局部变量、参数、返回值，往小地址增长 16KB └──────────────┘

用"大地址 / 小地址"来描述增长方向，比"上 / 下"可靠，因为换一张图，上下可能就反过来了。

为什么堆和栈要相向增长？（学习者自己算出来的）

代码占 1KB，剩下 15KB：

  • 固定边界（各 7.5KB）：程序 A 的栈要 12KB、堆只要 1KB → 栈不够用，堆却闲着 6.5KB
  • 相向增长：程序 A（栈 12 + 堆 1）、程序 B（堆 12 + 栈 1）都放得下

结论：中间的空闲空间由两边共享，不用事先猜各需要多少。

两端撞上了会怎样？

  • 栈撞上去：程序直接崩溃，也就是栈溢出（stack overflow）
  • 堆要不到空间：malloc 返回 NULL，由程序自己决定怎么处理（所以 malloc 之后要检查 p == NULL）

📐 虚拟地址 vs 物理地址（A层）

问题 结论
printf("%p", &x) 打印的是什么？ 虚拟地址。程序员能看到的所有地址都是虚拟地址
两个进程打印出同一个地址，会冲突吗？ 不会。同一个虚拟地址在两个进程里映射到不同的物理地址
虚拟地址空间有多大？ 由地址位数决定，不是 OS 的策略：32 位 → 232 字节 = 4GB
"8GB 内存"说的是什么？ 是容量（楼里有多少房间），不是地址（某个房间的门牌号）
空着的虚拟地址需要物理内存吗？ 不需要物理内存。这就是"稀疏"的意思。100 个进程 × 4GB = 400GB，如果全要物理内存，8GB 的机器根本跑不起来

🎯 三个设计目标（A层）

  • 透明：进程看不到虚拟化的存在，以为自己独占物理内存
  • 效率：时间上不能让程序变慢太多，空间上不能为了虚拟化占用太多额外内存
  • 保护：进程之间互不影响，进程也不能影响操作系统本身（也就是隔离）

"为什么要虚拟化"（历史需求）和"三个目标"（做到什么程度才算好）是两个不同的问题，不要混在一起回答。

🔧 谁负责翻译和保护？

🔗 和受限直接执行（LDE）连起来

OS 要靠时钟中断才能拿回 CPU ▼ 说明进程运行的时候，OS 不在场 ▼ 没办法每次访问内存都由 OS 检查（每秒几亿次，每次都陷入内核会慢得没法用） ▼ 只能交给硬件：每次访问时自动翻译和检查；OS 负责设置和管理

所以答案是 OS + 专门的硬件，只说"交给操作系统"只对了一半。

⚖️ CPU 虚拟化 vs 内存虚拟化

CPU 虚拟化（进程） 内存虚拟化（地址空间）
真实的资源 只有 1 个 CPU 只有 1 块物理内存
给进程的假象 我独占这个 CPU 内存由我独占
怎么共享 按时间：轮流用 按空间：划分成不同部分，同时用
靠什么实现 时钟中断 + 上下文切换 OS + 专门硬件做地址翻译

学习者自己的总结："一个进程同一时间只能独占 CPU，而不同进程同一时间可以独占内存的不同部分。"

🛠️ 实践验证：亲眼看虚拟地址

int x = 3; // 栈 int *p = malloc(sizeof(int)); // 堆 printf("code : %p\n", (void *)main); printf("heap : %p\n", (void *)p); printf("stack: %p\n", (void *)&x);
--- run 1 --- run 2 --- run 3 code : 0x10271c460 code : 0x102148460 code : 0x1009c8460 heap : 0x102d6db40 heap : 0x102661b40 heap : 0x101129b40 stack: 0x16d6e22a8 stack: 0x16dcb62a8 stack: 0x16f4362a8
  • 预测 code < heap < stack：✔ 猜中
  • 预测是虚拟地址：✔ 猜中。栈在 0x16d... 附近，超过 6GB，因为这台机器是 64 位的
  • 每次运行地址都变：这是 ASLR（地址空间布局随机化）。攻击程序需要事先知道栈、代码在这个进程自己的虚拟地址空间里的位置，才能精确地跳过去执行；位置每次随机，攻击就很难命中。它和物理地址没有关系
  • 最后 3 位不变：随机化是以"页"为单位整体平移的（这台 arm64 Mac 的页大小是 16KB），页内的偏移量保持不变。分页章节会详细讲（C层，现在知道就好）

⌨️ 打字默写检查

合上资料，先在框里打出答案，再展开参考答案对照。脑子里默念不算哦～

1. 从早期系统到地址空间抽象，中间经历了哪几步？每一步是为了解决什么问题？
参考答案

早期系统（只有 OS 和一个程序）→ 多道程序（提高机器利用率）→ 时分共享（交互性；最早靠把内存存到磁盘，太慢）→ 多个进程同时留在内存（出现保护问题）→ 地址空间抽象。

2. 地址空间、虚拟地址、物理地址是什么关系？地址空间由哪几部分组成？
参考答案

地址空间是 OS 给进程的抽象（整体），包含代码、堆、栈；其中每个位置的编号是虚拟地址；虚拟地址由 OS + 硬件翻译成物理地址（内存上真实的位置）。

3. 堆和栈分别往哪个方向增长？为什么要相向增长？
参考答案

堆往大地址长，栈往小地址长。中间的空闲空间由两边共享，谁需要就给谁用；如果固定边界，就会出现一边不够用、另一边闲着的情况。

4. 三个设计目标是什么？各用一句话解释。
参考答案

透明：进程感觉不到虚拟化的存在。效率：时间上不能太慢，空间上不能占用太多额外内存。保护：进程之间、进程和 OS 之间互不影响（隔离）。

5. 为什么地址翻译必须有硬件帮忙？请联系 LDE 回答。
参考答案

OS 要靠时钟中断才能拿回 CPU，说明进程运行时 OS 不在场。OS 没办法检查每一次内存访问，如果每次都陷入内核，程序会慢得没法用。所以由硬件在每次访问时自动翻译和检查，OS 负责设置和管理。

6. CPU 虚拟化和内存虚拟化最大的不同是什么？
参考答案

CPU 按时间共享：同一时刻只有一个进程用 CPU，大家轮流用。内存按空间共享：同一时刻不同进程各自占用内存的不同部分。

🎯 盲点自查

⚠️ 元层级薄弱点：今天两次把层级弄错

  • 第一次："地址空间是虚拟地址的划分方式"，把整体和组成部分颠倒了
  • 第二次：把 TLB 当成"地址翻译的机制"。TLB 只是让硬件翻译得更快的缓存，属于优化技巧，不是机制本身
  • 共同的根源：先抓住一个听说过的名词，没有先确认它在哪一层。以后遇到新名词，先问一句："它是要做的事，还是帮这件事做得更好的工具？"

本次学习中暴露的其他易错点

  • "8G 就是固定的内存地址"：8G 是容量，不是地址
  • "虚拟地址可能 10G 或 20G，取决于实现方式"：已自己算出纠正，大小由地址位数决定
  • "为什么要虚拟化"和"三个目标"混答：一个是动机，一个是评判标准
  • 历史链漏了时分共享：多道程序追求利用率，时分共享追求交互性
  • "安全交给操作系统"：只对一半，要加上"专门硬件"
  • "空着的空间不需要内存"：要说准确，是不需要物理内存
  • 以为 ASLR 是为了防止推算物理地址：其实是让攻击者猜不到虚拟地址空间里栈和代码的位置
  • 用了还没学到的名词（页表、MMU、TLB）：一次是粘贴来的答案，一次是层级错误。先把本章的说法说准，后面的名词等学到了再用
