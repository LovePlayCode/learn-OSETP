第10章：多处理器调度（高级）

学习日期：2026-10-08

📌 核心问题

CPU 从 1 个变成 N 个，调度要多考虑什么？

单核调度只需要决定"先跑谁"；多核调度还要决定"放在哪个 CPU 上跑"。

新增的三个考量：缓存亲和性、扩展性（锁竞争）、负载均衡。它们互相牵制，没有一种方案能同时做到最好。

🧱 硬件背景（B层）

一条因果链

CPU 很快、内存很慢 │ 局部性让小缓存也能经常命中 ▼ 缓存（为"快"而引入）── 每个 CPU 各有一份 │ 多份副本 → 可能读到过期旧值 ▼ 缓存一致性（问题 / 目标） │ 靠什么实现？ ▼ 总线窥探（解法）── 缓存控制器监听总线，发现别人改了自己缓存的数据 → 标记失效或更新
  • 时间局部性：刚用过的数据很快会再用（循环里的 sum、i）
  • 空间局部性：用了某个地址，很快会用它附近的地址（a[0] → a[1] → a[2]）
  • 为什么不干脆去掉缓存：内存比缓存慢几十到上百倍，去掉缓存 CPU 大部分时间都在等内存；一致性交给硬件解决，值得

别忘了同步

硬件一致性只保证"读到新值"，管不住多个 CPU 同时修改同一个共享数据结构（比如同时从队列头取任务）。这需要加锁。

代价：CPU 越多，越多时间花在等锁、抢锁上，性能随 CPU 数量增加明显变差（注意不是"指数级"）。

🧲 缓存亲和性（A层）

进程和它上次运行的 CPU "处熟了"

进程在某个 CPU 上运行时，借助局部性，缓存里积累了它马上要用的数据。如果换到别的 CPU，这些缓存就用不上了，需要重新从内存加载，速度变慢。

调度原则：尽量让进程回到它上次运行的 CPU。

别和这两个概念混淆

  • 缓存命中 / 未命中：缓存本身的工作方式（数据在不在缓存里）
  • 缓存一致性：正确性问题（会不会读到旧值）
  • 缓存亲和性：性能问题（换了 CPU，之前热好的缓存白热了）

📥 单队列调度 SQMS（A层）

做法：所有 CPU 共用一个任务队列，哪个 CPU 空闲了，就去队列里取下一个任务。

✔ 实现简单：单核的调度策略几乎不用改就能搬过来

✔ 负载天然均衡：谁空了谁去取，不会有 CPU 闲着

✘ 扩展性差：所有 CPU 抢同一把锁

✘ 破坏亲和性：进程会在各个 CPU 之间来回跳（亲和性本身是好东西，问题在于 SQMS 破坏了它）

补救：给单队列加亲和性机制

让大部分任务固定在同一个 CPU 上，只让少数任务迁移来平衡负载。例如 4 个 CPU、5 个任务时，A~D 各自固定在一个 CPU 上，只让 E 在各个 CPU 之间轮转。

学习者自己的设计：每个任务记录 lastCpu，如果上次的 CPU 有空就交给它。这就是亲和性机制的核心思路。

但它只补了亲和性，没有解决锁竞争：大家依然在抢同一把锁。

📚 多队列调度 MQMS（A层）

做法：每个 CPU 有自己的队列，新任务按某种规则放进其中一个队列（随机放，或者放进任务最少的队列），然后每个 CPU 各自调度自己的队列。

✔ 扩展性好：每个队列平时只被自己的 CPU 访问，基本没有锁竞争

✔ 亲和性好：任务一直待在同一个 CPU 上

✘ 负载不均：某个 CPU 的队列空了就闲着，别的 CPU 却还在排长队

负载不均 → 迁移 → 工作窃取

工作窃取：任务较少的队列时不时去看一眼别的队列，如果对方明显比自己多，就从那边搬一个或几个任务过来。

  • 检查太频繁：偷看别人的队列要拿别人队列的锁，抢锁一多，就失去了 MQMS 的初衷（扩展性）
  • 检查太少：负载长时间不均，CPU 空转

阈值没有标准答案，是系统策略设计里常见的"黑魔法"。

两层权衡

要不要迁移任务？ 缓存亲和性 ⟷ 负载均衡 多久检查一次？ 扩展性 ⟷ 负载均衡

迁移过来的任务在新 CPU 上缓存是冷的，所以工作窃取本质上是牺牲一点亲和性，换取负载均衡。

⚖️ SQMS vs MQMS

维度 单队列 SQMS 多队列 MQMS
缓存亲和性 差：任务在 CPU 间来回跳 好：任务固定在一个 CPU
扩展性 差：所有 CPU 抢一把锁 好：各用各的队列和锁
负载均衡 好：谁空了谁去取 差：需要靠迁移 / 工作窃取补救
实现复杂度 简单 复杂（负载均衡难做）

🐧 Linux 的三种调度器（C层）

调度器 维度①：任务怎么分给 CPU 维度②：单个 CPU 上先跑谁
O(1) 多队列 基于优先级，类似 MLFQ
CFS（完全公平调度） 多队列 确定性的比例份额，类似步长调度
BFS 单队列（三者中唯一） 比例份额，基于 EEVDF（更复杂）

🔗 两个正交的维度

"单队列 / 多队列"和"MLFQ / 比例份额"回答的是两个不同的问题，可以自由组合。

这也解释了学习中出现过的一个混淆："多级反馈队列"的"多级"按优先级分层，"多队列"的"多"按 CPU 来分，不是同一回事。

⌨️ 打字默写检查

合上资料，先在框里打出答案，再展开参考答案对照。脑子里默念不算哦～

1. 缓存一致性、缓存亲和性分别是什么问题？各自由谁来解决？
参考答案

一致性是正确性问题（多份缓存副本可能读到旧值），由硬件解决，例如总线窥探。亲和性是性能问题（换 CPU 后缓存要重新加载），由操作系统调度程序解决：尽量让进程回到上次运行的 CPU。

2. 单队列调度的两个好处、两个缺点分别是什么？
参考答案

好处：实现简单；负载天然均衡。缺点：所有 CPU 抢同一把锁，扩展性差；任务在 CPU 之间来回跳，破坏缓存亲和性。

3. 多队列为什么扩展性好？它最大的问题是什么？怎么补救？
参考答案

每个队列平时只被自己的 CPU 访问，基本没有锁竞争。最大的问题是负载不均。补救方法是迁移，典型做法是工作窃取：任务少的队列去看别的队列，对方明显更多时就搬几个任务过来。

4. 工作窃取检查太频繁、太少分别会怎样？为什么频繁检查会变慢？
参考答案

太频繁：偷看别人的队列要拿别人的锁，抢锁变多，丢掉了 MQMS 扩展性好的初衷。太少：负载长时间不均，有的 CPU 空转。

5. 工作窃取本质上是在哪两个目标之间做权衡？
参考答案

缓存亲和性和负载均衡：被搬走的任务在新 CPU 上缓存是冷的，牺牲一点亲和性来换负载均衡。（"多久检查一次"是另一层权衡：扩展性和负载均衡。）

🎯 盲点自查

本次学习中暴露的易错点

  • "局部性"写成"局限性"：两次写错。局限性是缺点，局部性是访问集中在一个小范围
  • "缓存损耗"一词混了两个问题：正确性（一致性）和性能（亲和性）要分开
  • 把缓存命中 / 未命中当成亲和性：亲和性说的是"进程和 CPU 的关系"
  • "多级"和"多队列"混用：从 MLFQ 带过来的词，两者维度不同
  • 抢锁的主语：抢锁的是 CPU，不是进程
  • "指数级下降"：用词过头，书里只说随 CPU 数量增加明显变差
  • 对比表自相矛盾：前一题刚说"多队列不抢锁"，后一题又填"扩展性差"。答题时要回头核对自己的结论
  • 工作窃取的因果链："频繁检查会变慢"中间那一环是"要拿别人队列的锁"
  • Linux 三种调度器：没有记住（C层，用时查阅即可）
